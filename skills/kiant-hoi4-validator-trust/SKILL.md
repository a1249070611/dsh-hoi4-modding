# 校验器报的错，该信几分

工具报错不等于你的 mod 报错。它会冤枉人，而且冤枉的方式有规律。

先记住一句：**全绿不代表没问题，满屏红也不代表都是你的问题。**

## 一、先分清三种情况

拿到一屏报错，别急着逐条改。先做个分类：

| 报错内容 | 判断 | 怎么做 |
|---|---|---|
| 这个写法原版里也有 | 大概率是工具误报 | 先跳过，但要记住它 |
| 只在你文件里出现 | 真问题 | 按报错改 |
| 说某个键/spirit/科技不存在 | 多半是真的 | 去原版找同名实现对照 |
| 同一句话重复几千行 | 通常是缺 BOM 或语法崩了导致的连锁 | 先修第一个，别管后面的 |

判断「原版里也有」的方法：把报错里提到的那个字段名、写法、文件名，用
`kiant_hoi4_kb_search` 到原版里搜一遍。搜到了，就是工具的问题。

## 二、满屏红字的三种典型来源

**缺 BOM。** 一个没有 UTF-8 BOM 的 `.yml`，游戏会整份忽略，校验器也会把它报成
几千条缺键。这种情况下几千条报错其实只有 1 个原因。先检查 BOM。

**语法没闭合。** 少一个 `}`，从那一行往后整个文件都被判为异常。同样是
一个原因引发成百上千条。先找 `unclosed` 那条。

**条件块写法。** `desc`、`title`、`icon` 可以写成一串条件分支，工具早期版本认不出
这种写法，会报「缺键」或「找不到 sprite」。原版里这种写法有几百处（国策 icon 108 处、
决议 icon 66 处、事件 title/desc 232 处）。如果你的报错集中在这些字段上，基本可以
判定是误报。

## 三、怎么确认是误报

最可靠的确认方式是**去原版找同样的写法**。

```bash
# 报错说某个国策的 icon 找不到，去原版看同样的写法长什么样
kiant_hoi4_kb_search "icon = {" kind=md
kiant_hoi4_kb_lookup kind=focus
```

原版自己都这么写、游戏跑得好好的，那你的写法就没问题。

另一个办法是跑 `kiant_hoi4_self_check`。它把原版游戏当模组跑一遍，把
「原版都通不过的检查」列出来——那些规则本身就是过严的，你的 mod 撞上了也不必改。

## 四、哪些报错可以先不管

按这个优先级处理，别按报错列表的顺序：

1. **error 里带「unclosed」「BOM」「无法解析」的** → 先修，它们会引发连锁
2. **本地化缺键** → 修，这是玩家能直接看到的
3. **贴图/sprite 找不到** → 修，进游戏是粉黑方块
4. **原版也报的** → 最后看，很可能不是你的问题
5. **info 级别** → 可以不看

## 五、什么时候该怀疑工具

出现下面任一情况，先别改 mod，先怀疑工具：

- 报错总数超过你文件数的十倍
- 同一个字段被报了几百次
- 报错说「不存在」，但你在原版里搜到了
- 报错指向的行号，那里写的东西看着完全正常

这时候去查错题本：

| 症状 | 查这条 |
|---|---|
| 校验报大量假阳性，满屏红字 | `EB-016` |

## 六、一个前提：严格度上限

校验器最多只能和引擎一样严。引擎能跑的写法，工具报错就是工具的责任。

这个结论有实测：把原版游戏喂给校验器，1.19.4.2 上跑出 1838 条 error，
其中绝大多数是原版真实的本地化缺失（1000 多个 idea 待在 `hidden_ideas` 里，
玩家根本看不到）。这些「错误」游戏照样跑。

所以遇到报错时的正确心态不是「我哪里写错了」，而是「这条报错站不站得住」。
