# DEVN-010 每次同步都全量重建索引

## 它想解决什么

改完文件后索引不更新，`kb_search` 搜不到新内容。最直觉的方案：每次同步都全量重建，保证索引一定最新。

## 思路

```
改文件 → kb_build（全量） → 索引必然正确
```

逻辑上无懈可击，实现上也简单。

## 为什么没被采用 / 不确定在哪

**太慢。** 全量重建要索引：

- 原版游戏文件（数千个）
- 已装模组（可能上万）
- 本地 notes + refs（几百）

实测量级：几分钟。而**增量重建只要几秒**。

具体对比（EB-017 的真实场景）：

```bash
# 全量：几分钟，因为要重扫原版 6000+ 文件
# 增量：几秒，跳过游戏目录
kiant_hoi4_kb_build  only=notes,refs  skip_game=true
```

原版文件极少变动（只有游戏更新时），没有理由每次重扫。

## 如果要用，怎么验证

其实**已经验证过了，结论是"不该用"**。这个条目留着是为了记录判断依据。

如果要进一步验证：在同一个项目上分别计时全量与增量，记录耗时比例。

## 备注

**这个思路的吸引力在于"正确性优先"。** 它确实保证索引正确，代价是时间。

但开发循环里的时间成本是会累积的：如果每改一次都要等 3 分钟，一天改 20 次就是 1 小时。**这种情况下"稍微不精确但快"的方案反而更对**——只要保证增量覆盖了所有会变的部分。

正确的策略是分场景：

| 场景 | 用哪种 |
|---|---|
| 改了自己的 notes / refs | 增量 `only=notes,refs skip_game=true` |
| 装了新模组 | 增量，只加那个 mod 源 |
| 游戏更新了 | 全量 |
| 首次建库 | 全量 |
