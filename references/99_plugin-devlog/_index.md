# 插件开发日志

## 这个目录为什么不和错题本放在一起

`91_error-book/` 和 `92_solutions/` 回答的问题是：**我做的 mod 出问题了，怎么办。**

这个目录回答的是另一个问题：**开发这个插件本身出问题了，怎么办。**

两件事看起来都是「修 bug」，但读者完全不同：

| | 错题本 / 方案库 | 这个目录 |
|---|---|---|
| 主体 | 做 HOI4 mod 的人 | 改这个插件代码的人 |
| 症状长什么样 | 游戏里图标是粉黑方块 | 自检里某条断言恒真 |
| 检查手段 | 进游戏看、看 error.log | 跑 `selftest.py`、跑变异测试 |
| 修完怎么验 | 再进一次游戏 | 自检全绿 + 变异全捕获 |
| 谁需要读 | 所有使用者 | 只有维护者 |

混在一起的代价很实际：一个做国策的 modder 检索「图标显示不对」，会同时命中
「GFX 键缺失」和「DDS 头部校验算错」两条。后者他一条也用不上，还得先读懂
什么叫做校验器假阳性才能排除它。**这不是信息多，是噪音。**

所以编号也分开了：这里用 `DEVB-`（development bug）和 `DEVN-`（development note），
和 mod 侧的 `EB-` / `SOL-` 不共用序列。搜 `EB-` 前缀永远不会命中这里。

## 这些东西对 modder 还有用吗

有一小部分有用，但要看角度。

`DEVB-025` / `DEVB-027` 记的是「校验器比引擎更严，把原版合法的写法报成错」。
一个用本插件的人遇到满屏红字时，需要的结论是「这是工具的毛病，不是你的 mod 坏了」，
以及「哪些报错可以先忽略」。这类信息**已经写进了 `91_error-book/EB-016`**
（校验报大量假阳性），从 modder 的视角重新讲了一遍。

这里保留的是原始记录：我当时怎么发现、怎么定位、改了哪几行。那是维护者需要的
上下文，对 modder 是无关细节。
