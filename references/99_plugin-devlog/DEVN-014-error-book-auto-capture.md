# DEVN-014 排障结束后自动生成错题本条目

## 它想解决什么

错题本（`91_error-book/`）的价值取决于**有没有持续记录**。但实际排障时：问题解决了就赶紧继续干活，写记录这件事一定被推到"以后"。

而"以后"往往不会来。等想起来时，"当时试过什么"这段已经彻底忘了——恰恰这段最值钱。

## 思路

在排障流程的末尾加一步自动化：

```
问题解决 → 触发记录 → 从对话/日志里提取结构化信息 → 生成 EB-NNN 草稿
```

可提取的要素：

| 要素 | 来源 |
|---|---|
| 症状 | 用户最初的描述 / error.log 原文 |
| 错误做法 | 本次对话里试过但失败的步骤 |
| 根因 | 最后确认的原因 |
| 方案 | 最终生效的修改 |
| 验证 | 确认修好的判据 |

技术上，如果 agent 参与排障，这些信息本来就在上下文里——只是没人去整理。

## 为什么没被采用 / 不确定在哪

1. **时机难定。** 什么算"问题解决了"？agent 自己判断容易误判，问用户又打断流程
2. **质量难保证。** 自动提取的"根因"可能只是猜测，而错题本的第一原则是「不写没有实证的条目」
3. **草稿仍需人工过。** 如果还要人改一遍，那和直接写有多大区别？

第 2 点最要紧。错题本条目的价值在准确，一份掺了猜测的错题本会误导后来者，比没有更糟。

## 如果要用，怎么验证

做一个最小版本：

1. 排障结束后，agent 输出一份 **结构化草稿**（不是直接写文件）
2. 草稿列在对话里，明确标注"以下内容待你确认"
3. 用户确认/修改后才写入 `91_error-book/`

验证标准：连续记录 5 次，其中至少 3 次用户只做小幅修改就接受（说明提取的信息基本准确）。

## 备注

**"降摩擦"比"全自动"更现实。**

全自动生成错题本听起来好，但错题本的核心约束是准确——自动生成的东西要么准确（难），要么需要人改（那自动化的收益就打折）。

折中方案是「生成草稿 + 人工确认」：把整理工作自动化（这部分是机械劳动），把判断留给人和实证。

顺带一个更简单的做法：**在 `validate_mod` / `analyze_error_log` 的输出里，直接给出"要不要记一条错题本"的提示**，附上可复制的模板。成本极低，但能显著提高记录率。
