# DEVN-013 把校验器在原版全量数据上跑一遍

## 它想解决什么

校验器报假阳性（错题本 `EB-016`）。已知的一类假阳性是 `decision_category` 跨文件重名——引擎允许，校验器却报错。

靠人逐条判断哪些是假阳性，成本高且不可持续。想要一个自动化办法。

## 思路

**原版游戏文件是"正确写法的黄金样本"。** 原版能跑，说明它的写法合法。

所以：

```
把所有校验规则在原版全量数据上跑一遍
→ 报出来的每一条，都是假阳性（因为原版是合法的）
→ 这些就是需要修正启发式的规则
```

这个思路的价值：**自动生成假阳性样本集**，不用等用户来报。

更进一步：把原版跑出来的结果作为回归基线。以后改校验器，基线报错数不应该增加。

## 为什么没被采用 / 不确定在哪

有几个未验证的假设：

1. **原版是否真的 100% 合法？** 可能原版也有 bug 或历史遗留的非标准写法
2. **原版的合法写法，在 mod 里是否也合法？** 大概率是，但没验证
3. **原版数据量大**（6000+ 文件），跑一遍要多久？如果太慢，不适合放进日常流程

第 1 点最关键。如果原版本身有 10% 的不规范写法，那这个方法会把这些也算进"假阳性"，导致规则被放宽得过头。

## 如果要用，怎么验证

1. 选一条已知会报假阳性的规则（`decision_category` 重名检测）
2. 只在原版 `common/decisions/` 上跑这一条
3. 检查报出来的每一条：真的都是合法重名吗？有没有混着真问题？

验证标准：报出的条目中，假阳性占比 > 90% 才说明这个方法可用；如果有大量真问题混入，说明"原版全合法"这个前提不成立。

## 备注

**这个思路的通用形式是「用已知正确的数据集来校准检查器」。**

在编译器、linter、类型检查器的开发里这是标准做法（叫 "differential testing" 或 "corpus testing"）。把它用到 HOI4 mod 校验上，逻辑是通的。

一个更轻量的替代方案：不用全量原版，只挑 **10 个原版文件**（覆盖各个类型）做"小基线"。跑得快，也能抓到明显的假阳性。
