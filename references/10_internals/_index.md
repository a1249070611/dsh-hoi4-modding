# 10 引擎底层

这一域回答「**为什么引擎这么干**」——不是「怎么写才能生效」，而是「引擎内部按什么规则
处理这些东西」。知道规则才能预判，而不是照抄模板后祈祷。

这是全库最难写的一域，因为**没有官方文档**：`documentation/` 里只有 effect/trigger
清单，不讲加载器和渲染器。这里每一条都是靠实测和交叉验证得出的，标注了验证方法。

## 本域 6 条最重要结论

1. **引擎对语法错误极其宽容，但宽容的方式不对称。**
   文件末尾少 `}` → 容忍（EOF 隐式闭合，原版 14 个文件这样）；
   多 `}` → 在该行截断解析；运算符写错（`>=`）→ **静默忽略整条语句**。
   所以「改了没生效」比「报错」常见得多。依据：`tools/kiant-hoi4-lint.py` 扫原版 2224 个文件实测。

2. **键名大小写不敏感，标识符大小写敏感。**
   `add_namespace = BBA_Switzerland` 配 `id = BBA_switzerland.1` 能跑；
   `Hidden = yes`、`Picture = ...` 也能跑。但 sprite 名折叠大小写就找不到了。
   校验器比引擎严，报出来的都是误报。详见本页末节。

3. **加载顺序决定覆盖结果，同名文件的覆盖是整文件级的。**
   mod 里放一个同路径文件，原版那个**整个被替换**，不是逐行合并。
   想改原版文件里的一个数值，必须把整个文件复制过来改——这也是为什么
   「改一个小数值」的 mod 常常几百 KB。

4. **本地化是「键 → 值」的扁平表，不区分文件来源，后加载的覆盖先加载的。**
   所以同一个 key 在多个 yml 里出现时，生效的是加载顺序最后一个。
   原版 2114 个 yml、259700 条词条，全部拍平到一张表里。

5. **所有 `.txt` 在内存里被拍平成「定义表」，不是保留文件结构。**
   引擎启动时把 `common/` 下所有定义读进内存的索引，运行期只查索引。
   这就是为什么改完必须重启游戏，热重载只对 `console` 命令有效。

6. **中文检索必须按 2 字滑窗，不能整串匹配。**
   这条不是引擎的，是本库索引层的：`code` 表用 FTS5 unicode61（整词），
   `text` 表用 trigram（三字相邻）。中文不写空格，整串匹配要求字字相邻，
   `国策树坐标` 这种组合必然 0 命中。

## 怎么验证一条「引擎行为」

没有文档，只能靠对照实验。可靠的做法是**找一个原版的大样本，统计分布**：

```bash
# 例：验证「原版用 DXT5 还是 32bpp」
python tools/kiant-hoi4-dds.py scan gfx/interface
#    → 16923 个里 16773 个是 32bpp，DXT5 只有 43 个

# 例：验证「relative_position_id 是 delta 还是绝对」
#   用重叠数当判据，哪种解释的重叠少，哪种就是对的
#   结果：raw 8440 / 单层 6680 / 递归 140 → 递归正确
```

**不要靠「我试了一次能用」下结论**。单个样本可能是巧合，分布才是规律。

## 最省力的验证法：把原版当 mod 跑

上面那些是「针对单个假设做实验」。还有一个**一次性覆盖全部假设**的办法：

```python
import checks
r = checks.validate_mod(VANILLA_ROOT, deep=False)   # 原版目录直接当 mod 喂进去
print(r["summary"]["errors"], r["summary"]["warnings"])
```

原版是「已知正确」的语料。所以判据是单向的：

| 结果 | 说明 |
|---|---|
| 原版跑出大量 error / warning | **校验器错了**，不是原版错了 |
| 原版跑出 0 条 | 至少没有系统性误报（**但不保证查得全**） |

**为什么这条比单点实验更值得先做**：单点实验要你先想到那个假设；
把原版跑一遍，等于让 60366 个真实文件同时质疑你的每一条规则。

2026-11-06 用这个方法一次抓出 6 类系统性误报（11694 → 2079 条 error，
降 82%），明细见 `99_plugin-devlog/DEVB-025-vanilla-as-testcase.md`。

**假阳性比假阴性更致命。** 假阴性用户进游戏会发现；假阳性会让用户
直接不看报告——1 万条 error 等于没检查。所以「零误报」的优先级高于「全覆盖」。

一个反直觉的推论：**校验器越保守，越要拿原版试。** 保守意味着大量
「不确定就报错」，而这恰恰是假阳性的温床。

**但「降到 82%」不是终点。** 同一份语料再跑一遍，把剩下的逐条看，
才发现还有 140 条是同一性质的问题。修完一轮就收工，是这个方法最容易漏的一步。

## 同一个字段，值可能是标量，也可能是块

这是解析 Clauewitz 脚本时最容易踩的坑，而且踩了**不会报错**，只会静默少读一部分。

同一个字段名，在原版里常见三种形态：

```
# 1) 标量
icon = GFX_focus_foo

# 2) 条件块（sprite 名当语句键，条件是值）
icon = {
    GFX_focus_a = { has_government = democratic }
    GFX_focus_b = yes
}

# 3) 条件块（sprite 名写在 key = 里）
icon = { key = GFX_decision_x trigger = { original_tag = USA } }

# 4) 可重复多次的块（每个变体一个 text 键）—— 事件 title / desc
desc = { text = some.key.den trigger = { tag = DEN } }
desc = { text = some.key.gen trigger = { always = yes } }
```

原版 1.19.4.2 实测分布：

| 字段 | 标量 | 块 |
|---|---|---|
| event `desc` | 6629 | **214** |
| event `title` | 6826 | **18** |
| focus `icon` | 10297 | **44** |
| decision `icon` | 3654 | **66** |

**四条读取纪律**（少一条就会错）：

1. **`get_all` 不是 `get_one`。** 同名语句可以重复多次，只取第一个必丢。
2. **`as_text()` 遇块返回空串，这不等于「没写」。** 必须单独判断 `isinstance(v, Block)`。
3. **看结构再取键：** 有 `key =` 就只收它（且立刻收手）；否则收**顶层**语句键。
4. **不要 `walk()` 深挖。** 条件表达式在值里，深挖会把 `has_government`、`OR`
   这些词当成 sprite 名。

**为什么这条值得单独记**：块形式是少数情况（`desc` 里只占 3%），
但漏掉它的代价是双向的——一边误报缺键（140 条），一边漏检引用（112 处）。
少数情况不等于可以忽略，因为它们的失败方式是**静默**的。

细节与实证见 `99_plugin-devlog/DEVB-026-value-may-be-block.md`。

## 键名和标识符的大小写不是一回事

读脚本时这两类东西必须分开处理，混在一起必然出错。

### 键名（字段名、命名空间）：引擎**不敏感**

原版里真实存在大小写不一致的写法，游戏照常运行：

```
events/BBA_Switzerland.txt:30    add_namespace = BBA_Switzerland   ← 大写 S
events/BBA_Switzerland.txt:73    id = BBA_switzerland.1            ← 小写 s（55 个全这样）
events/USA.txt:1487              Hidden = yes                     ← 首字母大写
events/*.txt                     Picture = ...                    ← 8 处
```

所以读取字段要用大小写不敏感的比较（本项目里是 `cw.get_one_ci()` / `cw.get_all_ci()`）。
用精确匹配的后果不是"读不到就跳过"，而是**把字段当成没写**，进而误报
"事件缺标题"、"选项缺名称"、"图标没引用"。

原版实测这类大小写异常只有 10 处，比例极低，但它们会稳定复现，
所以不能靠"应该没人这么写"来跳过。

### 标识符（sprite 名、id、路径）：**保持原样**

`sprite` 名、事件 id、文件路径都是要找东西的键，折叠大小写会找不到目标。
读 `icon` 时，字段名可以不敏感，但取出来的 sprite 名必须原样保留。

### 顺带一条：行分隔符

`str.splitlines()` 认的换行符包括 `\v` `\f` `\x85`(NEL) `\u2028` `\u2029`，
**远多于**引擎认的 `\n` / `\r\n`。原版本地化文本里混进一个 NEL 字符，
`splitlines()` 就会把一行劈成两半，后半截没键名前缀，报「无法解析的行」。
解析本地化时按 `\n` 切，但**先归一化 `\r\n`**，否则 Windows 文件每行尾部留 `\r`。

细节与实证见 `99_plugin-devlog/DEVB-027-case-and-syntax-tolerance.md`。
