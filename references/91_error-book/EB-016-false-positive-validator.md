# EB-016 校验报大量假阳性

## 症状

跑校验器（lint / validate_mod），报出几十上百条"错误"，但你逐条核对后发现**这些写法在原版里就有**，完全合法。

典型例子：`decision_category` 在不同文件里重名，被报成"重复定义"。

## 错误做法（我试过的）

1. 相信工具，把合法写法按"错误"改掉 → 破坏了原本正确的结构，问题变多
2. 完全忽略工具输出 → 连真问题也漏了
3. 关掉某类检查 → 该类真问题以后都查不到了

## 根因

校验器用**启发式判断**推断语义，而引擎的实际规则比启发式宽松。已知的几类假阳性：

| 假阳性类型 | 引擎实际规则 |
|---|---|
| `decision_category` 跨文件重名 | **合法**。引擎按名合并，这是官方惯例 |
| `common/decisions/categories/` 下的块被判为决议 | 该目录**只定义类别，不定义决议**。结构铁律优先于字段猜测 |
| 角色块被误认为重复 id | 角色块有**三种布局**：`char{...}` / `char{instance{...}}` / `TAG{char{...}}`，固定深度解析会把 `instance`、`portraits` 当成角色 id |
| `target_root_trigger` 被判为决议独有字段 | 它在 `on_map_area` 里也有，不能作为决议签名 |

## 标准化方案

1. **不要直接改代码。** 先把假阳性记下来，判断它属于上表哪一类。

2. 对号入座后，在项目里记一条约定（写进该项目的 `AGENTS.md` 或本目录新条目），说明"这类是合法的，原因如下"。

3. 确认是真阳性再改。

判断真假的通用方法：

```bash
# 在原版文件里搜同样的写法。原版有 = 合法
grep -rn "同一种写法" <GAME_DIR>/common/ | head
```

**原版是最好的判据。** 如果原版大量使用某种写法，你的校验器报它错，错的是校验器。

## 怎么防止反复踩

- 遇到一条假阳性，就在你的项目笔记里记一笔，写清「哪个写法是合法的、为什么」。
  下次再报同样的错，不用重新判断一遍
- 一批报错里假阳性占多数时，先只处理确定是真问题的那几条，别为了「清空报错列表」
  去改合法写法
- 拿不准的先去 `kiant_hoi4_self_check` 跑一遍原版，看这条规则在原版上灵不灵

## 怎么确认自己判断对了

改完之后两边都要看：

1. 真问题该消失的消失了
2. 原来被误报的合法写法，现在不报了

只看第 1 条不够。把合法写法改成「不报错的样子」，同样是「报错列表变干净了」，
但你把原本正确的东西改坏了。

## 备注

**不要盲信工具。**

实测数据：某 4871 文件的项目，初版校验报 70056 条，逐条甄别后确认绝大多数是
假阳性加单一根因重复，最终收敛到 98 条真问题。

一个爱报假阳性的校验器会训练使用者忽略它的全部输出，那它就彻底失效了。
所以遇到大量报错时，你的第一反应应该是「这些是真的吗」，而不是「我该怎么改」。

> 校验器为什么会误报、规则怎么修的，属于插件维护范围，记在
> `99_plugin-devlog/DEVB-025` 和 `DEVB-027`。写 mod 不需要读。
