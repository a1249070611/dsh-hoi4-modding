# EB-012 error.log 里同一句话刷几千行

## 症状

`error.log` 打开有 7 万条 error，翻了几百行发现全是同一种错误，只是文件路径不同。

```
[19:01:12][parser.cpp:1234]: Error: Unknown trigger-type "check_variable" in ...
[19:01:12][parser.cpp:1234]: Error: Unknown trigger-type "check_variable" in ...
...（重复 6000 次，路径不同）
```

## 错误做法（我试过的）

1. 逐条读第一屏，试图一条条改 → 70056 条，读完就已经失去耐心，而且每条看起来都不一样（路径不同）
2. 用编辑器正则批量替换 → 因为不知道根因，替换规则写错，把正常的也改了
3. 直接忽略，认为"反正都是同一种" → 漏掉了混在里面的真问题

## 根因

日志洪水通常是**单一根因被逐文件重复报告**。上例中某个 effect/trigger 在几千个文件里被引用，引擎对每一处都报告一次。

但也可能混着**多种**根因，外观相似。所以不能直接忽略。

## 标准化方案

```bash
# 1. 先聚类，不逐条读
#    MCP: kiant_hoi4_analyze_error_log
```

它按「源文件 + 消息模板」聚类计数，把 70056 条收敛成几十个类别。这一步是关键——**从 7 万降到几十**之后才能开始分析。

2. 按聚类结果排序，先处理**条数最多的一类**。往往改一处根因就能消掉上万条。

3. 每修完一类就重跑一次日志分析，看剩余类别。**不要一次改多个根因**，否则无法归因。

4. 从 70056 收敛到个位数后，剩下的往往是真问题（且各不相同）。

## 预防

- 每次改完内容立刻跑 `kiant_hoi4_validate_mod`，不要把错误攒到几十个文件后一起看
- 大项目定期清空 `error.log` 再跑一次，避免旧错误干扰

## 验证

修完后 error.log 行数应该有量级下降。判据：从 7 万降到 98 是正常结果（本库实测数据），降到 0 反而不正常（可能有检查没跑到）。

## 备注

**核心方法是「先聚类再分析」，不是「先看第一条」。**

本库有一次实测：某个汉化子模组（4871 文件）从 **70,056 条**收敛到 **98 条真问题**，全过程就是分类处理。剩下的 98 条里有 5 类典型假阳性（决策类别跨文件重名等），详见 `EB-016`。

**不要被条数吓到。** 7 万条里通常只有十几个根因。
