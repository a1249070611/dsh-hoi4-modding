# EB-013 error.log 干净但功能不对

## 症状

功能不工作，但 `error.log` 一行相关报错都没有。你反复看日志，怀疑自己看错了文件。

## 错误做法（我试过的）

1. 以为日志路径不对，去找别的 log 文件 → 就是这一个，确实没有
2. 以为要开 `-debug` 才有详细日志 → 开了还是没有
3. 反复重启游戏，希望"这次能报出来" → 不会
4. 因为没报错，转而怀疑自己看错了现象 → 浪费更多时间

## 根因

**HOI4 引擎有大量静默失败路径。** 已知的至少包括：

| 静默失败 | 表现 | 详见 |
|---|---|---|
| 科技 folder 的 `available` 用运行时条件 | 连线全消失，不报错 | EB-003 |
| 同 ID 被其他 mod 覆盖 | 内容被替换，不报错 | EB-007 |
| `.yml` 缺 BOM | 整个文件被忽略，不报错 | EB-001 |
| 图标 GFX 名不存在 | 部分情况下只是不显示 | EB-005 |
| `replace_path` 整目录替换 | 原版内容消失，不报错 | EB-009 |

共同点：**失败发生在"数据供给"层，而渲染/执行层仍正常运转**，所以引擎认为一切正常。

## 标准化方案

日志干净时，**不要继续查日志，改用结构化校验**：

```bash
# 1. 全类型校验（比默认更全，含科技/贴图/模型/图标/界面/事件钩子/国家历史）
#    MCP: kiant_hoi4_validate_mod  deep=true
```

```bash
# 2. 针对具体症状做专项审计
#    MCP: kiant_hoi4_list_overrides       覆盖关系是否符合预期
#    MCP: kiant_hoi4_scan_localisation    本地化完整性
#    MCP: kiant_hoi4_find_duplicate_ids   ID 撞车
```

3. 用 `preview` 做离线结构核对：

```bash
# MCP: kiant_hoi4_preview
# 国策树按真实坐标渲染、连线画出、本地化覆盖率一并呈现，不用开游戏
```

4. 如果结构校验也全绿，做**对照实验**：临时移除你怀疑的部分，看现象是否消失。这是判断静默失败最快的实证方法。

## 预防

- 每改完一批内容就跑 `validate_mod deep=true`，不要只靠游戏内观察
- 关键结构（科技 folder、覆盖关系）改动后专门跑对应审计

## 验证

判据不是"日志干净"，而是"结构校验通过 + 现象正确"。

## 备注

**这一条是整个错题本的方法论基础。**

> 日志干净 ≠ 没有问题。它只说明"引擎没有遇到它认为需要报告的情况"。

本库记录的多个最贵的坑（科技连线消失、覆盖失效、本地化整文件失效）**全部**是静默失败。所以调试顺序应该是：

```
结构化校验 → 专项审计 → 离线预览 → 对照实验 → 最后才是看日志
```

而不是反过来。
